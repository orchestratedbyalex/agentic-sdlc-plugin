# Agent evals

Evals for the plugin's **own agents**: golden target-repo fixtures with labelled
outcomes, driven headless through the real plugin (`claude -p --plugin-dir .`), asserted
mechanically on each gate report's machine-parsable `VERDICT: PASS|FAIL` line — never an
LLM judging an LLM. A "live run worked once" is a demo; these are the repeatable check
that a gate agent still catches what it exists to catch.

> **Billed.** Every case spawns a real `claude` session (your account, your configured
> default model unless `--model` says otherwise). That is why evals are opt-in behind
> `SDLC_EVALS=1` and are **never** part of `node --test` — CI and contributor machines
> stay model-free.

## Run

```bash
node evals/run.mjs --list                         # list cases (free)
SDLC_EVALS=1 node evals/run.mjs                   # run every case on your default model
SDLC_EVALS=1 node evals/run.mjs --case <id>       # one case (repeatable / comma-separated)
SDLC_EVALS=1 node evals/run.mjs --model <model>   # route to a specific model
SDLC_EVALS=1 node evals/run.mjs --keep            # keep the fixture workdirs for inspection
```

Each run writes `evals/results/<stamp>/<case>/` (gitignored): the full stream-json
`transcript.ndjson`, the extracted subagent `report.md`, and `meta.json`
(verdict, failures, cost, duration). Exit code 0 = every case matched its label.

## How a case runs

1. The fixture is copied to a throwaway temp dir and given a deterministic baseline
   commit (fixtures carry no `.git`; a fixture's `_eval-uncommitted/` overlay, if any,
   is applied *after* the commit — that is how diff-reviewing agents get an
   uncommitted "change under review").
2. `claude -p` starts **inside the workdir** with `--plugin-dir` pointing at this repo,
   and is instructed to dispatch exactly one subagent
   (`agentic-sdlc:<agent>`) via the Agent tool. The runner sets
   `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`: the CLI runs dispatches in the background
   by default since 2.1.198, which would route the report through a completion
   notification whose summary completeness is undocumented — synchronous dispatch keeps
   the full final message in the Agent tool_result.
3. The subagent's final message is extracted from the stream — from the Agent
   tool_result, or from its completion `task_notification` if a dispatch still ran in
   the background (defense-in-depth); the top-level model's relay is only a last-resort
   fallback (`reportSource` in `meta.json` says which path was used).
4. `evaluateCase` asserts the labelled `VERDICT:` plus any `mustMatch`/`mustNotMatch`
   patterns (e.g. the verbatim Execution Evidence contract).

## Fixture rules (enforced by a structure test)

- Under `evals/`, **no** file may match `node --test` discovery — no `*.test.mjs`/
  `*-test.mjs`/`test.mjs` names and no directory named `test/` — because the root
  test runner executes every match, fixtures included. Fixture suites live in
  `spec/*.check.mjs`, invoked by explicit path or glob from the fixture's
  `package.json`.
- Every fixture is a complete miniature target repo: `CLAUDE.md` (the commands the
  agent will trust), `package.json`, and `docs/requirements/sdlc-metadata.yml`
  generated by the state script **at the lifecycle point the case needs** — phases 1–4
  completed for the Verify gate agents, or mid-Develop (authors completed, the reviewer
  `in_progress`, the plan registered via `plan-add`/`plan-active`) for a review case.
- A case may set `prompt:` to mirror what the orchestrator would insert into the
  dispatch (e.g. `PLAN PATH: …` + `TIER: …` for the Develop code reviewer). Any
  `docs/…` path such a prompt names must exist in the fixture — a structure test
  enforces it, so plan renames fail at test-time, not bill-time.
- A fixture's `_eval-uncommitted/` overlay is applied AFTER the baseline commit: its
  files arrive as the uncommitted working-tree diff. That is how a diff-reviewing agent
  gets "the change under review" (`git status`/`git diff` show exactly the overlay).
- Fixtures must stay dependency-free (`npm install` never runs).

## The matrix

Three gate agents across five labels:

| Case | Agent | Fixture | Label | Why it exists |
|------|-------|---------|-------|---------------|
| `analyzer-clean-pass` | static & dynamic analyzer | `clean` | `VERDICT: PASS` + verbatim evidence quoting the build's own output | guards against a gate that fails everything |
| `analyzer-broken-build-fail` | static & dynamic analyzer | `broken-build` | `VERDICT: FAIL` + `BLOCKER` | unit tests green, production build exits 1 — the proxy trap (invariant 3) |
| `analyzer-no-build-honest-pass` | static & dynamic analyzer | `no-build` | `VERDICT: PASS` + explicit "no build step / interpreted" | the agent must say so and smoke-run, not invent a build |
| `code-reviewer-hardcoded-secret-fail` | Develop code reviewer | `hardcoded-secret` | `VERDICT: FAIL` + a security `BLOCKER` naming the secret + Execution Evidence | the uncommitted diff hardcodes the API key the plan's Security Considerations say comes from an env var — check 6 is a blocker at every tier, and check 9 must still run |
| `regression-zero-tests-fail` | Verify regression tester | `zero-tests` | `VERDICT: FAIL` + the zero-collection quoted in evidence | the test command exits 0 while collecting **zero** tests (glob rot: specs renamed, `spec/*.check.mjs` matches nothing) — a vacuous green is a FAIL (invariant 3) |

Extending the matrix = one fixture dir + one row in `cases.mjs` (the structure tests
verify every case names a real agent and a complete fixture, including any plan path
its prompt references). Natural next candidates: a WAIVED-never-agent-issued behavioral
case (the structure tests pin the text; an eval would prove the behavior), and coverage
for more gate agents (validation reviewer's independent re-run, release reviewer).
